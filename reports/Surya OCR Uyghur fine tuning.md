# Teach Surya Uyghur with Kitabim's own corpus

Kitabim can fine-tune Surya on Uyghur, but its database cannot supply training labels directly. It has about **236.7k OCR'd pages from 633 books**, a **1.46M-word lexicon** and **294 curated wrong→right correction rules**. What it lacks is a human-verified line of ground truth. Every page's text came from Gemini Vision, which was prompted to reflow paragraphs. That erases the line-end hyphen fragments Kitabim most needs to teach, and Gemini may also silently normalize spelling. The workable path has four parts. First, build a small, human-verified, line-level evaluation set. Second, restore the dictionary-validated de-hyphenation and confusion-set correction that were deleted from the OCR client in commit `e15a26a8`, as an immediate fallback. Third, generate training data from two sources: Gemini text re-aligned to Surya's own line output, and synthetic renders that deliberately split words at line ends and swap confusable letters. Fourth, fine-tune the current Surya 2 model in block mode with LoRA, using generic Qwen3.5 VLM tooling. That last step is untested: Surya 2.x is a ~650-690M-parameter Qwen3.5-architecture VLM, Datalab publishes **no training script** for it, and no one has publicly reported fine-tuning it. Two blockers apply before any of this ships. The weights' modified OpenRAIL-M licence passes its restrictions on to fine-tuned weights and arguably to OCR output, and it bars use above $5M revenue or funding or by a competing product. And without verified ground truth, no claimed improvement can be measured.

## Surya 2 is a Qwen3.5 VLM with a weak Uyghur baseline

The model Kitabim runs is different from the one most online fine-tuning advice describes. The client pins `surya-ocr==0.22.1`, which loads **`datalab-to/surya-ocr-2`**, a `Qwen3_5ForConditionalGeneration` model. It has a 12-layer ViT encoder and a 24-layer hybrid-attention decoder, and it handles OCR, layout and tables through fixed prompts rather than language tags ([config.json](https://huggingface.co/datalab-to/surya-ocr-2/resolve/main/config.json); [v0.20.0 release](https://github.com/datalab-to/surya/releases/tag/v0.20.0)). Every Surya fine-tuning script, fork and tutorial online (`finetune_ocr.py`, Ollsoft, whynotkimhari) targets the retired v0.15–0.17 recognizer. Those scripts broke even for that model ([Issue #474](https://github.com/datalab-to/surya/issues/474); [Issue #482](https://github.com/datalab-to/surya/issues/482)). For Surya 2.x the README says only: "If you want help finetuning Surya on your own data... reach us at hi@datalab.to" ([Surya README](https://github.com/datalab-to/surya)).

Two facts make a fine-tune promising. Datalab's own multilingual table scores **Uyghur at 34.1% (Surya 2) and 32.9% (Surya 2.5)**, against 74.5–74.9% overall, so the starting point is weak and there is room to improve ([multilingual.md](https://raw.githubusercontent.com/datalab-to/surya/master/static/docs/multilingual.md)). And the tokenizer is a character-level `WordLevel` vocabulary in which every Uyghur letter is a single token. This includes ئ, ە, ۆ, ۇ, ۈ, ۋ, ې, ى, ڭ and ژ, plus `-`, U+2010, the soft hyphen and tatweel ([surya-ocr-2 tokenizer.json](https://huggingface.co/datalab-to/surya-ocr-2/resolve/main/tokenizer.json)). So no vocabulary surgery is needed. The weakness sits in the visual and language modelling, which training data can fix. Upgrading to v0.23.0 / Surya 2.5 would not improve Uyghur accuracy. It does cut loop rates from 3.8% to 0.1% of requests hitting the output limit ([v0.23.0 release](https://github.com/datalab-to/surya/releases/tag/v0.23.0)). Surya 2.5 added ~20k multi-character tokens, but none are Arabic-script, so Uyghur pages remain long, one-token-per-character sequences. Whichever base is chosen, it should be fixed before training, because prompts and chat templates are the model's "training-time contract".

Because the checkpoint is a stock Qwen3.5 safetensors model that loads via `AutoModelForMultimodalLM` ([HF model card](https://huggingface.co/datalab-to/surya-ocr-2.5)), generic Qwen3.5 vision tooling should work. Unsloth supports bf16 LoRA on the 0.8B tier at about **3 GB VRAM**. It warns against 4-bit QLoRA and requires the chat template and EOS token to match between training and inference ([Unsloth Qwen3.5 docs](https://unsloth.ai/docs/models/qwen3.5/fine-tune)). Surya's own `build_gguf.py` and its `SURYA_GGUF_LOCAL_MODEL_PATH` setting suggest a route back into Kitabim's llama.cpp client. That route is inferred from the code and not documented. Whether Surya 2's single MTP layer survives a PEFT round-trip and GGUF conversion is also unverified.

The training format matters for both target problems. Surya 2.x has two modes. Full-page mode emits `<div data-label data-bbox>` HTML with normalized boxes. Block mode takes a layout-block crop with the fixed prompt `"OCR this block image to HTML."`. Block mode is the practical training target because it needs no bounding-box labels. Mixing in some full-page examples, labelled with the model's own boxes and corrected text, should help keep full-page behaviour from degrading.

## The hyphen hallucination is a language prior completing non-words

Uyghur, unusually among Arabic-script orthographies, hyphenates across line breaks. In modern books a short straight stroke "similar in form to a straight kashida (U+0640)" sits at the line end, which is the left edge in right-to-left text, even after non-connecting letters ([Hudson citing Hahn, W3C www-style](https://lists.w3.org/Archives/Public/www-style/2014May/0391.html)). The fragment before the mark is by construction not a word. An autoregressive decoder with a strong lexical prior "completes" it. A measured study of historical English OCR found the VLM (Qwen2.5-VL-7B) beat TrOCR on CER (0.60% vs 1.05%) but showed "lexically motivated over-normalisation" that TrOCR did not. It also found that short lines were the hardest slice for both models (3.93% vs 5.79% CER) ([arXiv 2602.14524](https://arxiv.org/html/2602.14524)). Line-end fragments are exactly short, non-lexical tokens, so Surya's hyphen hallucinations fit this failure mode.

The Kitabim client already documents a second symptom. The docstring of the now-unused `engine/line_ends.py` says full-page Surya "reflows each block into running text, so a line-end hyphen ('ھەز-' / 'رىتى') comes back as 'ھەز - رىتى'" ([clients/kitabim-ocr/engine/line_ends.py](../clients/kitabim-ocr/engine/line_ends.py)). The client worked around this by re-recognizing the left 60% of each detected line, then joining `p1-p2` when `p1p2` is in `words` and `p1-p2` is not. Commit `e15a26a8` removed that de-hyphenation step (`git show e15a26a8^:clients/kitabim-ocr/engine/text_cleanup.py`). It left `engine/line_ends.py` and `engine/dictionary.py` in the tree but unused, and `ocr_page(valid_words=…)` a dead parameter.

The best-supported training-time remedies attack the prior. Nougat randomly replaces ground-truth tokens, which "significantly reduced" repetition collapse ([Nougat](https://arxiv.org/pdf/2308.13418)). LOCR randomly skips 0–5 target tokens and reports a stronger effect ([LOCR](https://arxiv.org/pdf/2403.02127)). No published study measures training on synthetic hyphen fragments. The recipe follows directly from the mechanism, though, and is cheap. Wrap Uyghur text to a line width and force a break inside the last word on a fifth to a third of lines. Shape `prefix-` with HarfBuzz so the prefix takes its correct form before the non-joining hyphen. Then label it literally as `prefix-`, with the next line starting from the suffix. Shaping needs care: when Pillow's Raqm backend is active, the common `arabic_reshaper` + `python-bidi` preprocessing double-shapes text. One small test saw 14 of 15 renders break ([HF arshape discussion](https://huggingface.co/datasets/syamjithnk/arshape/discussions/2)). Rendering must go through a real OpenType stack (Pango or Pillow+Raqm, checked with `PIL.features.check("raqm")`).

The training data must keep diplomatic hyphenation. Transcription practice such as TEI and DTA records line-end hyphens explicitly, and calls "transcribe the word as if whole" inaccurate ([Balisage](https://balisage.net/Proceedings/vol17/html/Bauman01/BalisageVol17-Bauman01.html)). If targets contain the rejoined word, the fine-tune will learn exactly the hallucination Kitabim wants to stop. Kitabim already decided that de-hyphenation belongs in the OCR client. So the model should emit `prefix-` faithfully and leave joining to deterministic code.

## Kitabim's confusion data describes Gemini's errors, not Surya's

Kitabim's richest confusion signal is real but comes from the wrong engine. Three sources exist, each counted with difflib over the local DB:

- the 294 active `auto_correct_rules`;
- 5,239 applied corrections joined to those rules;
- 677,904 open `page_spell_issues` with dictionary-validated candidates.

All three agree that the waw-family vowels dominate, followed by dropped ى/ي and then the ك/ڭ/گ, ن/ڭ and ر/ز pairs ([models.py](../packages/backend-core/app/db/models.py); [spell_check_service.py](../packages/backend-core/app/services/spell_check_service.py)).

| Edit (OCR → correct) | Curated rules | Applied corrections | Open issues (first candidate, unverified) |
|---|---:|---:|---:|
| و→ۇ | 150 | 816 | 126,437 |
| ۆ→ۇ | 30 | 1,502 | 15,586 |
| ∅→ى (dropped vowel) | 26 | 2,202 | 174,508 |
| ۇ→و | 24 | 116 | 36,011 |
| و→ۆ | 9 | 404 | 5,716 |
| ك→ڭ | 7 | — | 26,288 |
| ن→ڭ | — | — | 15,518 |
| ر→ز / ز→ر | — | — | 14,253 / 12,481 |
| و→ۋ | 4 | — | 7,763 |

These numbers have three limits. First, almost all of this text was OCR'd by Gemini, whose `OCR_PROMPT` already names these confusions and injects the auto-correct rules into the prompt ([prompts.py](../packages/backend-core/app/core/prompts.py)). Second, the open-issue candidates are generated only from the hard-coded `_OCR_PAIRS` and `_VOWEL_INSERTIONS` lists, so the table cannot show confusions those lists do not contain. **ي/ئې, ز/ژ, and the hamza-seated ئو/ئۇ/ئۆ/ئۈ distinctions are absent from `_OCR_PAIRS` entirely.** No statistic exists for them anywhere in the database. Third, Surya's own deleted cleanup rules show a different, Arabic-biased profile: final ب for پ (مەكتەب→مەكتەپ), ه for ە, and م for ؟ after interrogative مۇ. This profile does not appear in Gemini text. The table is a sound prior for weighting synthetic minimal pairs and oversampling. It is not a measurement of what Surya gets wrong, and it cannot replace one.

Real-word confusions set a hard ceiling on post-processing. Where both the ۇ and ۆ variant of a word are valid, a dictionary check passes the error. The historical-OCR study found many errors survive lexical checks for this reason ([arXiv 2602.14524](https://arxiv.org/html/2602.14524)). That is why a visual fix, fine-tuning, is still needed after a lexicon fallback is in place. On the data side, the literature favours targeted augmentation of rare or confusable classes over loss reweighting, which can hurt majority classes ([oracle-bone OCR survey](https://arxiv.org/pdf/2411.11354)). Persian Pixel identifies dot count and placement on shared-skeleton letters as the central fragility under degradation. It tests no remedy, though ([Persian Pixel](https://arxiv.org/html/2607.20385)). Kitabim should therefore oversample real words containing the target letters several-fold. It should also add a small minority (under ~10%) of single-letter "swap" non-words, so the model must read the mark rather than guess from the skeleton. Degradation should be strong enough to stress the dots of ڭ and ژ and the marks of ۇ/ۆ/ۈ, but not so strong that the label becomes unreadable from the image.

## Gemini page text becomes training data only after realignment

Each resource maps onto a specific role, and none of them is ground truth as stored:

| Resource | Size (local DB) | Role in the fine-tune | Caveat |
|---|---|---|---|
| `pages.text` + source PDFs in GCS `uploads/{book_id}.pdf` | 235,949 non-empty pages, ~330 MB text | Pseudo-labels after alignment; in-domain text for synthetic rendering | Paragraph-reflowed, hyphens already resolved, `[Header]/[Footer]` markers on 200k pages, possible normalization |
| Pages with a human `updated_by` | ~13.9k pages, mostly 128 books | Candidate pool for the verified eval set | `updated_by` is also set by reprocess clicks; no proof of a text edit |
| `words` | 1,463,208 (25,636 hyphenated) | De-hyphenation validator; confusion-set corrector; synthetic text filter | Provenance undocumented; real compounds like ئاز-ئازدىن must not be joined; read-only |
| `auto_correct_rules`, `page_spell_issues` | 294 rules; 5,259 corrected; 677,904 open | Confusion prior for oversampling and channel weights | Reflect Gemini's errors |
| `history_dictionary`, `names_dictionary`, `dictionary` | 6,436 / 7,074 / 20,299 | Proper-noun and term coverage for lexicon checks and synthetic text | Small; terms only |
| `pages.prev_text` | 0 rows locally | (before, after) pairs if populated in prod | Written only by LLM spell-check, overwritten each run |

The proven recipe for turning clean page text into line labels comes from KITAB/OpenITI Arabic work. Run an OCR engine for line positions and noisy text, align the clean transcription to it with passim, and assign each line its clean span ([KITAB project](https://kitab-project.org/OpenITI,-OCR,-and-Textual-Criticism/)). The historical-English study built 68k of its 195k training lines this way ([arXiv 2602.14524](https://arxiv.org/html/2602.14524)). For Kitabim the steps are:

1. Download the PDF and extract the embedded ~300 dpi page image rather than the 1.5× (~108 dpi) render Gemini saw.
2. Run Surya's layout and recognition.
3. Character-align (edlib or Needleman–Wunsch) the Surya output to the cleaned Gemini text.
4. Cut the Gemini text at Surya's block or line boundaries.

Two corrections are mandatory. Wherever Surya's raw output shows a line ending in a fragment, the aligned whole word must be re-split and the hyphen re-inserted, or the line dropped. Otherwise the data teaches the hallucination. And lines should be kept by **agreement** between Surya and the aligned text (for example under ~15% CER), not by Surya's confidence. Confidence filters preferentially discard the hard, rare lines this project exists to fix. A PP-OCRv6 historical adaptation hit that problem ([arXiv 2609.20064](https://arxiv.org/pdf/2609.20064)), and SoftCTC notes seed models are overconfident ([SoftCTC](https://arxiv.org/pdf/2212.02135)). Born-digital PDFs with a text layer, like `tests/fixtures/test_book_3_txt.pdf`, give exact line text and boxes via PyMuPDF. A one-off scan of the corpus for text layers is therefore cheap and worth doing.

Comparable fine-tunes suggest the required scale is modest. QARI-OCR LoRA-tuned Qwen2-VL-2B (rank 16, one epoch, one A6000) on 10k–50k synthetic Arabic renders across 12 fonts and three degradation levels, and reached **CER 0.061** on a 200-page printed test. Diacritic-rich text drove the gains, and 4-bit quantization hurt fine-grained recognition ([QARI-OCR](https://huggingface.co/papers/2506.02295)). Fine-tuning GPT-4o on just **500 in-domain Urdu samples** cut WER by 6.13 points ([arXiv 2505.13943](https://arxiv.org/abs/2505.13943)). A Tatar Tesseract model reached 1.84% CER on books by training first on synthetic lines, then on real scans ([yasalma/tatar-ocr-tesseract](https://huggingface.co/yasalma/tatar-ocr-tesseract)). Fonts matter more than corpus size. Tesseract's `uig` model was rendered only in Arial Unicode, DejaVu and FreeSerif ([okfonts.txt](https://raw.githubusercontent.com/tesseract-ocr/langdata_lstm/main/uig/okfonts.txt)), so Kitabim should render in UKIJ Tuz/Tuz Tom and ALKATIP book faces ([Devroye Uyghur type](https://luc.devroye.org/uyghur.html)). Their licences must be confirmed before rendered data is redistributed. No public printed-book Uyghur OCR dataset exists to borrow. SUST/RUST is scene text with unclear provenance ([HF dataset](https://huggingface.co/datasets/lht12311/Uyghur_OCR_SUST_RUST)). The only Uyghur TrOCR model is CC-BY-NC-ND ([patkaiist/Uyghur_TrOCR](https://huggingface.co/patkaiist/Uyghur_TrOCR)).

## Two blockers gate everything: licence and ground truth

**The licence is the first gate.** The code is Apache-2.0, but the Surya 2/2.5 weights carry a modified OpenRAIL-M with three restrictions. It prohibits use by any entity with more than **$5M gross revenue** or **$5M total funding**, except for personal or research use. It also prohibits use "for any purpose" by anyone offering a product or service that **competes with Datalab**. It names fine-tuning explicitly as covered use. Its §8 share-alike clause applies the licence to "Derivatives of the Model" **and to "the Output and any derivatives… of the Output"** ([surya-ocr-2.5 LICENSE](https://huggingface.co/datalab-to/surya-ocr-2.5/resolve/main/LICENSE)). Kitabim is a book-digitization and Q&A platform, not a parsing API, so the non-compete clause probably does not apply. But "probably" is not enough for a model whose output would be stored in the corpus and possibly redistributed. A legal reading is needed before investing in training, and Datalab's managed-training offer is the commercial alternative. The cleanest hedge is to keep the data pipeline engine-agnostic. The same chat-format block data and LoRA mechanics apply unchanged to an Apache-licensed Qwen3.5-0.8B base, so Kitabim can train both and let a held-out Uyghur evaluation decide.

**Ground truth is the second gate.** No `is_verified` flag, revision table or CER tooling exists. The editor save path overwrites `page.text` without saving the prior version, and `updated_by` cannot separate a human edit from a reprocess click ([books_router.py](../services/backend/api/endpoints/books_router.py)). The only quantitative Surya claim in the repo is a rise in model *self-confidence* from ~0.75 to ~0.97 after switching engines. That is not accuracy. Gemini's own error rate has never been measured against a human reference. Every number a fine-tune produces will be meaningless until Kitabim owns a verified, diplomatic, line-level test set. That set must be held out by **book**, as the historical-OCR study did ([arXiv 2602.14524](https://arxiv.org/html/2602.14524)), and kept free of synthetic lines. The comparison in the SARD benchmark shows how a test-set provenance mismatch inflates results ([SARD summary](https://www.emergentmind.com/topics/sard)). One configuration issue should be ruled out first. The client caps full-page output at 2,500 tokens, roughly 2,500 Uyghur characters. Some dense pages would therefore fail as truncation that looks like looping. Issue #561 shows Surya 2 failing on a dense two-column Uyghur contents page ([Issue #561](https://github.com/datalab-to/surya/issues/561)).

## Recommended phased plan

| Phase | What to do | Exit criterion |
|---|---|---|
| **0. Unblock (1–2 weeks)** | Get a legal reading of the OpenRAIL-M terms (revenue, funding, non-compete, §8 Output share-alike) and decide whether to engage Datalab. Pin the base model (stay on Surya 2 / v0.22.1 unless loop rates justify 2.5) and log cap-hits separately from loops. Add a `jiwer`/edit-distance CER harness by extending `scripts/compare_ocr.py`, with fixed normalization: strip `[Header]/[Footer]`, fold ه→ە, ک→ك and presentation forms, keep ئ as U+0626. | Licence position documented; harness runs. |
| **1. Evaluation set** | Pick ≥5 held-out books stratified by era, font, scan quality, bleed-through, verse, footnote and TOC pages. Pre-fill lines with Surya output aligned to Gemini text, then have native speakers correct them **diplomatically**, keeping line-end `prefix-`. Target ≥1,000–2,000 lines overall. Add a hyphen slice of ≥300 line-end fragments (~±3.4 pp CI at 10% error) and a confusable slice of ≥100 occurrences per letter for ئو/ئۇ/ئۆ/ئۈ, ز/ژ, ۋ, ي/ئې, ك/ڭ. Find rare ژ and ڭ by corpus search. | Baseline Surya CER/WER, per-letter confusion matrix, fragment exact-match and inserted-char count recorded. |
| **2. Post-processing fallback (ship in parallel)** | Restore the lexicon-validated de-hyphenation from `e15a26a8^`: join only when `p1p2 ∈ words`, `p1-p2 ∉ words`, and the compound is not a hyphenated `words` entry. Add a confusion-set corrector that rewrites only **non-words**, within {و,ۇ,ۆ,ۈ,ۋ}, {ز,ژ}, {ي,ې}, {ك,ڭ,گ}, plus ب→پ word-finally, up to 2 substitutions, and only when one in-lexicon candidate clearly dominates. Add `names_dictionary`/`history_dictionary` to the lexicon. Use `words` read-only. Measure over-correction on the eval set. Use an LLM, if at all, only to choose among listed candidates. | Hyphen-slice and confusable-slice gains with over-correction below an agreed threshold. |
| **3. Training data** | (a) **Real:** extract native-dpi page images from GCS PDFs (exclude eval books), crop Surya layout blocks, align cleaned Gemini text, re-insert line-end hyphens, filter by agreement, oversample lines containing target letters or fragments. Prefer pages with human `updated_by`; add born-digital text-layer PDFs. (b) **Synthetic:** 10k–50k block renders from `pages.text` sentences through HarfBuzz in Uyghur book fonts. Force line-end splits on 20–30% of lines, oversample confusable words 3–5× using the confusion table as weights, add under 10% letter-swap non-words and 5–15% random-syllable lines, and degrade with Augraphy (ink bleed, bleed-through, blur, JPEG, 150–200 dpi downsampling). | Versioned dataset with provenance per sample; synthetic validation kept separate. |
| **4. Training route** | Block-mode SFT (`"OCR this block image to HTML."` → `<p>…</p>`) on Surya 2 with Unsloth or TRL bf16 LoRA on decoder **and** vision attention (not QLoRA), plus a small full-page replay set. Use Nougat/LOCR-style target perturbation (a few % of tokens replaced or skipped). Start clean, then raise degradation. Train an identical run on Qwen3.5-0.8B as the licence hedge. Export with `build_gguf.py` and verify the GGUF output matches the PyTorch output on the eval set. | Beats baseline + Phase 2 on overall CER and both slices, with no full-page or layout regression. |
| **5. Close the loop** | Change the editor save path to keep the prior text and mark pages as human-verified, so every proofread page becomes future ground truth. Mine hard examples from Surya-vs-verified disagreements for the next training round. | Ground truth grows without a dedicated labelling budget. |

## Conclusion

Kitabim's data is valuable for fine-tuning in a different way than it first appears. The 236k pages are not a labelled dataset. They are an **in-domain text corpus and an alignment target**, and their most useful property, clean reflowed paragraphs, is what disqualifies them as direct labels for the hyphen problem. The lexicon and correction tables have the same split role: as a prior and a validator they are excellent, but as a measurement of Surya they say little, and they are silent on ز/ژ, ي/ئې and the hamza-seated vowels. The scarce resource is a few thousand human-verified lines, not more pages. The cheapest long-term fix is a small schema change so that every editor save produces one.

The hyphen problem also has a clear order of fixes. The project already wrote and tested the deterministic fix, then deleted it. Restoring it, evaluated on a real hyphen slice, is the fastest win and the yardstick any fine-tune must beat. Fine-tuning should then aim to make Surya emit the fragment faithfully, not to make it rejoin words. In practice that means teaching the model to stop doing what a language model naturally does, which is complete words. Finally, the licence question may decide the base model more than accuracy does. Building the pipeline so it can train either Surya or an Apache-licensed Qwen3.5 base keeps that decision open until the evaluation set can settle it.

### `packages/backend-core/migrations/073_create_history_dictionary_staging.sql` (committed)

- **[blocking]** Migration number collision — `073_create_history_dictionary_staging.sql` (commit `fe8b7ee`, this feature) uses the same number as the already-committed, unrelated `073_add_conversations_soft_delete.sql` (commit `5b62145`). The migrations README explicitly says to "check migration number to avoid conflicts (use next sequential number)". This should be renumbered to the next free slot after what's already on disk (076/077/078 are also taken by this branch, so it would need to go after those, or be resequenced with the other three feature migrations). As-is, two migrations both claim "073" and any tooling/ops runbook that assumes one file per number will be confused about apply order.
- **[suggestion]** `category`, `entry_type`, and `status` are enum-like string columns (`VARCHAR(30)`/`VARCHAR(20)`) with no `CHECK` constraint, unlike the newer `078_create_batch_history_extraction_jobs.sql` which does add one for `status`. Add `CHECK (status IN ('pending','approved','rejected'))`, similarly for `category`/`entry_type`, both here and in the corresponding `HistoryDictionary`/`HistoryDictionaryStaging` ORM models (`packages/backend-core/app/db/models.py`).
- **[suggestion]** `history_dictionary_staging.book_id` has no `FOREIGN KEY` to `books(id)` (unlike `batch_history_extraction_jobs.book_id` added later, which does `REFERENCES books(id) ON DELETE CASCADE`). Staging rows become orphaned/unreferenced if a book is deleted. Also `book_id` has no index despite `DictionaryRepository.get_staging_terms()` filtering on it (`WHERE book_id = :book_id`) — add `CREATE INDEX idx_history_staging_book_id ON history_dictionary_staging(book_id)`.

### `packages/backend-core/app/db/repositories/dictionary_repository.py` (committed, unchanged in working tree)

- **[blocking]** `create_staging_term`, `approve_staging_term`, and `reject_staging_term` all call `await self.session.commit()` inside the repository method. Per the layering rule, the caller (service/endpoint) should own the transaction boundary, not the repo. As written, `bulk_approve_staging_terms` (router) causes N separate commits for N staging IDs, each one final — no way for the caller to batch or roll back a partial bulk operation.
- **[blocking]** `approve_staging_term` (lines ~226–285) contains real business logic — deciding whether to update vs. insert a live `HistoryDictionary` row, merging `sources` arrays with `dict`/`list` manipulation — inside a repository method. Per the "repos are CRUD only" rule this branching/merging belongs in `HistoryExtractionService` (or a new `HistoryReviewService`), with the repo reduced to plain fetch/insert/update calls.

### `packages/backend-core/app/services/history_extraction_service.py` (committed + working tree)

- **[blocking]** `_call_llm_extraction`'s fallback path (`except Exception as e: logger.warning(f"Fallback LLM extraction call failed/mocked: {e}"); return []`) swallows every possible failure (auth error, quota exceeded, malformed JSON, network timeout) and silently returns an empty entity list. `process_book_pages` then reports success with zero staged terms for that batch, with no observable signal that extraction actually failed. This should log at ERROR via `log_json` with the book/batch context, and either re-raise (so the calling worker job can mark the page/job failed and retry) or return a per-batch error marker the caller can act on.
- **[suggestion]** Uses `logger.warning(f"...")` (f-string) instead of `log_json(logger, level, "message", key=value)` — violates the observability convention used everywhere else in this codebase.

### `packages/backend-core/app/services/batch_history_extraction_service.py` (NEW, working tree)

- **[blocking]** `poll_and_process_batch_history_jobs` iterates over ALL active jobs, and for each job iterates over every extracted entity, calling `extraction_service._stage_entity(...)` (which internally calls `DictionaryRepository.create_staging_term`, which commits) — all using the single `session` passed in from the scanner (`services/worker/scanners/batch_history_poller_scanner.py` opens exactly one `async with async_session_factory()` for the whole poll cycle). The per-job `except Exception as exc:` (lines 288–296) logs the error but never calls `await session.rollback()`. If any DB-level error occurs mid-job (e.g. an integrity error from `create_staging_term`), SQLAlchemy will leave the shared `AsyncSession` in a `PendingRollbackError` state, and every subsequent job in the same poll cycle will fail with a cascading, unrelated error. Call `await session.rollback()` in the except block before `continue`, and consider giving each job (or at minimum each entity) its own session per the worker-job guideline.
- **[blocking]** No idempotency/retry protection around partial ingestion: if `poll_and_process_batch_history_jobs` raises partway through ingesting a job's output lines (e.g., entity #50 of 200), the job's `status` is never updated to `succeeded`/`failed`, so it stays in `submitted`/`running` and will be re-polled on the next scanner run — re-processing the same Gemini output from scratch. Because `_stage_entity` already committed entities 1–49 as new staging rows, the retry will run `find_matching_staging_term` against those, and mis-classify what should be the same term as `entry_type="enrichment"`, creating a second review-queue row that merges the term against itself. Track per-line/per-entity progress (e.g., an offset or a `custom_id` "already processed" set) or make staging idempotent on `(book_id, term, status='pending')`.
- **[suggestion]** No timeout/stale-job detection, unlike the sibling `batch_embedding_service.py` (`poll_and_process_batch_embedding_jobs`), which reads `embed_batch_timeout_hours` / `embed_batch_max_retry_count` from `system_configs` and force-fails jobs stuck past the timeout. A Gemini Batch job that never transitions out of `submitted`/`running` (dropped webhook, API hiccup) will poll forever with no way to recover. `migration 078` also has no `retry_count` column to support this. Add a timeout config + column, mirroring the embedding job pattern.
- **[suggestion]** Line 93: `content = (getattr(p, "cleaned_text", None) or getattr(p, "text", "") or "").strip()` — `Page` (in `packages/backend-core/app/db/models.py`) has no `cleaned_text` attribute at all, so this `getattr` always falls through to `text`. Harmless today (default `None`/`""` handles it) but it's dead/misleading code, likely copy-pasted from a different service; simplify to `(p.text or "").strip()`.
- **[suggestion]** `_stage_entity` is a "private" (underscore-prefixed) method of `HistoryExtractionService`, but is called directly from this separate module (`extraction_service._stage_entity(...)`, line 246). This is the right call to *reuse* logic instead of duplicating it (good), but reaching into a nominally-private method across modules is a layering smell — consider renaming it to a public method (`stage_entity`) since it's now part of the service's external contract.

### `packages/backend-core/migrations/078_create_batch_history_extraction_jobs.sql` (NEW, working tree)

- **[suggestion]** Not wrapped in `BEGIN; ... COMMIT;` unlike every other migration in this feature (073, 077) and most of the repo's migrations. The two statements (`CREATE TABLE` + `INSERT INTO system_configs`) aren't atomic as a result — if the `INSERT` fails (e.g., unique constraint edge case) the table creation still stands with no seed row. ## Summary

The core feature (extraction → staging → admin review/approve/reject) is functionally reasonable and reuses `_stage_entity` well between the synchronous and batch paths, avoiding logic duplication. The main risks are in the batch-processing extension: `batch_history_extraction_service.py`'s poller shares one session across all jobs/entities with no rollback on error and no idempotency guard against re-processing a job's output after a partial failure, and it has no timeout/stale-job recovery unlike its sibling `batch_embedding_service.py`. There's also a real migration-number collision at `073`, a stray dead-code duplicate of the router under `services/backend/app/`, and several i18n/layering gaps (`session.commit()` and business logic inside `DictionaryRepository`) carried over from the earlier committed work. Recommend addressing the blocking items — especially the session/rollback and idempotency issue in the poller and the `073` renumbering — before merge.
